## The 8 tools

### 1. Error Log Analyzer ⭐⭐⭐⭐⭐ (10 unique / 10 SEO) — build first, highest leverage
Paste a raw stack trace / console error / log line → regex-match against a signature database → **auto-link to the matching page in the site's own `/errors/` cluster** (~85 pages and growing). Highest-leverage tool on the list: makes the entire error-reference moat *actively discoverable* — paste what you actually see, get routed straight to the fix.
- **Data:** `data/error-signatures.json` — one record per `/errors/` page: `{ pattern: <regex>, slug, language }`.
- **Maintenance rule (HARD):** every new error page built in any future Phase 7 batch must add a signature entry here, or the Analyzer silently falls behind the cluster it's supposed to index.
- No match found → still show the parsed error type/message + a link to `errors.html` to browse, never a dead end.

### 2. Log Redactor ⭐⭐⭐⭐ (9 / 8) — fastest build, quick win
Paste raw logs → regex-redact common secret patterns (AWS keys, bearer/JWT tokens, API keys, emails, IPs, credit-card-like sequences) before pasting into a bug report, Slack, or an AI chat. Pure client-side regex substitution, no dependencies, strongly on-brand for the privacy-first positioning.

### 3. API Response Inspector ⭐⭐⭐⭐ (9 / 9)
Paste an API response (body, optionally headers) → flag missing/wrong `Content-Type`, missing CORS headers, inconsistent field casing (camelCase vs snake_case), null-vs-missing-field inconsistency, and **detect a paginated/enveloped response** (`{ data: [...], page, total }`). Complements existing pages: `errors/cors-no-access-control-allow-origin.html`, `errors/x-map-is-not-a-function.html` (envelope detection), `errors/cannot-convert-undefined-or-null-to-object.html`.

### 4. Docker Image Optimizer ⭐⭐⭐⭐ (8 / 9)
Paste a `Dockerfile` → static-analysis advisor (clarify in the UI: advisor, not an actual builder): bloated base image (`node:latest` → suggest `-slim`/`-alpine`), missing multi-stage build, `apt-get` without cleanup, poor `COPY` layer-caching order, missing `.dockerignore`.
- **Overlap note (unresolved):** ties to the Docker error cluster (Batch 5 Tier DK) and Phase 8's planned Docker templates generator — check for cross-link/shared-dataset opportunity once Phase 8 exists.

### 5. API Contract Diff ⭐⭐⭐⭐ (9 / 9)
Diff two OpenAPI/JSON-schema specs (or two raw API response samples) → classify each change as **breaking** (removed field, type change, now-required field) vs **non-breaking** (added optional field, new endpoint).
- **Reuse requirement (HARD):** build on the existing key-by-key diff engine already in `json-diff.html`/`js/json-diff-tool.js` — do not reimplement a differ from scratch. Extend with OpenAPI-aware semantics (path/method-level diffing, a breaking-change classifier layer).

### 6. Deployment Readiness Checker ⭐⭐⭐⭐⭐ (10 / 9)
Paste `package.json` (optionally a `Dockerfile`/`.env.example`) → checklist of readiness gaps: missing `start`/`engines`, no `.gitignore`, secrets-shaped values in a pasted `.env`, no health-check mentioned.
- **Overlap note (unresolved):** Phase 8 already plans a narrower `.env` validator + a static "Deployment Checklist" per tutorial. This tool is the broader, interactive superset — do not duplicate `.env` parsing twice; reconcile once both phases exist.

### 7. Project Health Checker ⭐⭐⭐⭐⭐ (9 / 9)
Broader than #6 — paste `package.json` → structural health signals: missing `license`/`repository`, no test/lint script, no `.gitignore`.
- **Design decision (must stay honest):** true "are my deps outdated" checks need live registry data, which conflicts with the pure-offline privacy-first framing. Resolved as an **optional, clearly-disclosed** live check against the public npm registry (package *names* only, never code/secrets — same privacy posture as a package manager), gracefully degrading to structural-only checks when offline or declined. Must be opt-in, never silent.

### 8. Error Relationship Graph ⭐⭐⭐⭐⭐ (10 / 8) — build last, highest effort, highest shareability
Interactive visualization of how errors commonly cascade or co-occur (e.g. CORS block → Failed to fetch → Cannot read properties of undefined). Highest backlink/shareability potential, highest build effort.
- **Implementation constraint (HARD):** hand-rolled, deterministic layout (fixed/curated positions or simple non-physics layout) — **not** a physics-simulated force-graph or a heavy charting dependency, to stay consistent with the site's no-build-step/vanilla-JS convention.
- **Data:** `data/error-relationships.json` (slug → related slugs + relationship type) — derive from the "Related Errors" links already present on every error page rather than maintaining a second, divergent dataset.
